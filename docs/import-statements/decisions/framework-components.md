## Locked-in v1 decisions

Each row anchors to a specific criterion or tiebreaker. These are the shapes locked in while specifying v1; the gate stays open for new rows.

### Criterion-3 override — admitting compiler-specific SFC ecosystems

Each of Vue / Svelte / Astro fails the *strict* reading of Criterion 3 (Framework-portable — works in every major toolchain for that language) because each requires its own compiler. The registry already accepts that trade-off for `.jsx` / `.tsx` (which require a JSX transformer). Treating Vue / Svelte / Astro the same way the registry already treats React + JSX is the design call. The dominant pattern in all three is default-import-as-component:

```typescript
import MyComp from './MyComp.vue';     // Vue 3 SFC
import MyComp from './MyComp.svelte';  // Svelte 5 SFC
import MyComp from './MyComp.astro';   // Astro component
```

…then `<MyComp />` in the template / JSX / Astro markup. The shape is identical across all three; the ecosystem-specific compiler handles the parsing. This is the resolution of the central Criterion-3 tension.

### Picker, dispatch, and source-acceptance decisions

| # | Decision | Justification |
|---|----------|---------------|
| 1 | Reuse the TS picker (`TYPESCRIPT_IMPORT_OPTIONS`) for `.vue` / `.svelte` / `.astro` destinations: **yes** | Vue `<script setup lang="ts">`, Svelte `<script lang="ts">`, and Astro frontmatter are all TypeScript — a strict subset of TS. The seven post-audit shapes (default / named / namespace / side-effect / type-only / inline-type / dynamic) cover the SFC import surface 1:1 with no semantic gap. `<script setup>` macros (`defineProps`/`defineEmits`/`defineSlots`), Svelte runes (`$state`/`$derived`/`$props`), and Astro frontmatter declarations are compiler macros / build-time code, not import statements. See the dedicated `script.*ImportStyle` rejection bullets below. *(Vue P1 #4, Svelte P2 #7, Astro P3 #9.)* |
| 2 | `.jsx` / `.tsx` / `.mdx` destinations accept `.vue` / `.svelte` / `.astro` sources: **yes** | Near-zero cost (one `case` each in the `buildAssetImportStatement` default-import group, `src/snippets/_react.ts:71-73`). Default-import-as-component is the correct shape. Use cases: mixed React+Vue via `defineCustomElement`, Svelte 5's `customElement` web-component export consumable by React, mixed React+Astro (e.g. Storybook stories for `.astro` components). No gating change needed — JSX/TSX/MDX destinations have no per-destination filter in the gating conjunction. *(Vue P1 #2, Svelte P2 #2, Astro P3 #5.)* |
| 3 | `.svelte.ts` / `.svelte.js` companion files: **handled by the standard TS/JS path** | `path.parse('foo.svelte.ts').ext` returns `.ts` — flows through the existing TS dispatch unchanged. Adding a `.svelte.ts` gating entry would shadow that natural dispatch. A one-line note lives in the shared `framework-component.ts` so future readers don't "fix" the perceived omission. Also in the rejection ledger below. *(Svelte P2 #8.)* |
| 4 | Single shared `framework-component.ts` builder (no `_framework.ts`, no per-framework `vue.ts`/`svelte.ts`/`astro.ts`): **yes** | The three destinations have identical default-import-as-component semantics, so one `buildSnippet` handles all three (dispatched together in `dispatch.ts`). The Phase 3 sketch had filed a shared `_framework.ts` helper as a Phase 3.x follow-up; the as-built extraction landed immediately and collapsed the three sketched ~30-line wrappers into one file, making a separate shared-helper module unnecessary. *(Astro P3 #10; realizes the Phase 2 "shared helper may emerge" note.)* |
| 5 | Vue/Svelte SFC-script placement override (constrain insertion to within the `<script…>`/`</script>` pair): **yes** | "Bottom" placement (via `IMPORT_INDICATORS`) handles the common case, but "Top" on files not leading with `<script>` was a latent issue. The shipped override (`insertSnippetAtSfcScript` in `insert-snippet.ts`, `computeSfcPlacement` in `placement.ts`) constrains Vue/Svelte insertion to within the `<script…>`/`</script>` pair, mirroring the Astro frontmatter override. `findSfcScriptBounds` prefers `<script setup`, falls back to bare `<script`, and synthesizes a `<script>`/`</script>` pair at line 0 if none exists. This is the shipped resolution of what Phase 2 decision #6 had filed as a latent issue, landing as the shared-fix-with-Astro that decision anticipated. *(Svelte P2 #6, shipped.)* |
| 6 | Astro frontmatter synthesis on empty / frontmatter-less `.astro` files: **yes, synthesize the fence** | The alternative (fall through + toast) produces a broken `.astro` file (import outside the `---` fence → compiler error). Synthesizing a `---`…`---` block at line 0 produces a valid file with zero user action. `insertSnippetAtAstroFrontmatter` synthesizes the fence when `findAstroFrontmatterBounds` returns `null`. *(Astro P3 #1.)* |
| 7 | Astro frontmatter detection precision: **strict trim equality** (`line.trim() === '---'`) | Simplest implementation, matches Astro's own gray-matter-based parser behaviour, rejects `--- text` lines (which Astro doesn't accept as fences). No practical false-positive risk from leading-whitespace lines. `findAstroFrontmatterBounds` matches on trimmed `---`. *(Astro P3 #2.)* |
| 8 | Astro within-fence Top/Bottom/Cursor: **honour the user's setting inside the fence** | Phase 3 decision #3 originally locked "override always inserts after the opening fence" (no cursor-inside-frontmatter detection). As built this was relaxed: the override honours the user's Top/Bottom/Cursor setting *within* the fence — **Top** inserts after the opening `---`; **Bottom** scans the frontmatter region for `IMPORT_INDICATORS` and inserts after the last match (falls back to after the opening `---`); **Cursor** inserts at the cursor line if inside the fences, else falls back to Bottom. The "Bottom within frontmatter" follow-up the original decision deferred was folded into the ship. `.astro` is always forced-frontmatter (the setting is honoured only as the within-fence position); the Astro override and the HTML/Markdown forced-cursor override are mutually exclusive. *(Astro P3 #3, relaxed and shipped.)* |
| 9 | Media-file / text-track sources accepted by framework destinations: **yes, in lockstep with the media work** | When media support shipped, `VUE_/SVELTE_/ASTRO_SUPPORTED_EXTENSIONS` each gained the agreed extensions in lockstep (spread `...MEDIA_FILE_EXTENSIONS` and `...TEXT_TRACK_FILE_EXTENSIONS`). No separate framework-side design work was needed. See [`media-files.md`](media-files.md) / [`../spec/media-files.md`](../spec/media-files.md). *(Vue P1 #5, Svelte P2 #9, Astro P3 #11.)* |
| 10 | Setting namespace for future framework-specific options: **deferred — no new setting in v1** | No Vue/Svelte/Astro-specific `package.json` setting is needed (TS-picker reuse eliminates the need, decision #1). If one ever surfaces, namespace it under `script.vue*ImportStyle` / `script.svelte*ImportStyle` / `script.astro*ImportStyle` — each ecosystem's import surface is script-like. This locks in "no new three-site sync surface for v1." *(Vue P1 #6, Svelte P2 #10, Astro P3 #12.)* |

## Things considered and rejected

Criterion-tagged rejections. New rejections must open with their criterion tag in parenthetical italics and cite either an Inclusion criterion (1–6) the shape fails or a Rejection criterion (A–F) from [`../CRITERIA.md`](../CRITERIA.md). Doc-local notes are acceptable when no criterion is a clean fit; flag them explicitly with a `*(Doc-local rejection — …)*` tag.

These are shapes evaluated and **declined** — not pending work. Deferred-but-intended framework items (PascalCase auto-naming and the joint SFC concerns: `.css`/`.scss`-into-SFC, `.ts`/`.js` destinations accepting SFC sources, `.md`/`.mdx` as a source for `.vue`/`.svelte`) are *not* rejections — they carry implementation intent and live in [`../future/framework-roadmap.md`](../future/framework-roadmap.md).

- **Auto-detecting project framework from `package.json`.** *(Doc-local rejection — wrong signal-content / brittle in mixed-stack repos; no single criterion is a clean fit.)* Could read `dependencies.vue` / `dependencies.svelte` / `dependencies.astro` and dispatch picker accordingly. Too brittle — monorepos / mixed-stack repos break the assumption. Stick to per-destination dispatch (destination file extension is authoritative).
- **A single combined "framework component" picker.** *(Fails Rejection Criterion F: Picker bloat with low marginal value — no UX win over per-destination dispatch.)* Across all three ecosystems the snippet shapes are identical (default-import-as-component). A combined picker offers no UX win; per-destination dispatch already routes correctly and lets each ecosystem evolve independently. (As-built: the three destinations collapsed into one shared `src/snippets/languages/framework-component.ts` builder — the single-builder collapse is the implementation of "no UX win from a combined picker," not a combined *picker*; each ecosystem still routes by its own destination extension.)
- **Vue 2 single-file components.** *(Fails Criterion 4: Modern best practice — Vue 2 EOLed end of 2023.)* Skip.
- **`.vue` SFCs with separate `.vue.ts` companion files** (a rare convention for splitting types out of the SFC). *(Doc-local rejection — `path.parse('foo.vue.ts').ext` is `.ts`, so the companion is already handled by the existing TS path; no new shape.)* The companion file is plain TS and is handled by the existing TS picker via the standard `.ts` path.
- **`.svelte.ts` / `.svelte.js` companion files as a separate gated extension.** *(Doc-local rejection — `path.parse('foo.svelte.ts').ext` returns `.ts`; a dedicated gating entry would shadow the natural TS dispatch with no semantic benefit.)* Tempting because the basename signals rune-eligible scope, but adding a `.svelte.ts` gating entry would shadow the natural TS dispatch with no semantic benefit. The plain TS path is correct for both source and destination roles.
- **Auto-detecting Svelte runes mode and adjusting import shapes.** *(Doc-local rejection — runes are SFC-body constructs that don't change `import` shape; no picker impact.)* Runes (`$state`, `$derived`, `$effect`) are SFC-body constructs that don't change the shape of `import` statements. No picker impact. Out of scope.
- **Solid (`.tsx` with Solid runtime), Lit (`.ts` with web components), Qwik (`.tsx` with `component$()`).** *(Doc-local rejection — all three reuse the existing `.tsx`/`.ts` extensions; no new gating needed, so no admission decision applies.)* The shape of imports for Solid / Lit / Qwik components is the same as any other TS/TSX default or named import.
- **Astro client directives** (`client:load`, `client:idle`, `client:visible`, `client:media`, `client:only`). *(Doc-local rejection — template-side hydration hints applied at usage sites, not in the import statement; out of scope for an import generator.)* Hints applied at usage sites (`<Counter client:load />`), not import-side. The import statement itself is unchanged. Out of scope.
- **Astro Server Endpoints / API routes** (`src/pages/api/foo.ts`). *(Doc-local rejection — plain TS files; handled by the existing TS dispatch, no Astro-specific gating needed.)* Plain TS files exposed under Astro's file-based routing.
- **Astro Content Collections** (`src/content/`). *(Doc-local rejection — content uses `.md` / `.mdx` / `.yaml` already covered by existing paths; the schema file is plain TS.)* Use `.md` / `.mdx` / `.yaml` for content with `src/content/config.ts` for schema. No Astro-specific gating needed — the existing Markdown / YAML paths cover content authoring; the schema file is plain TS.
- **`.mdx` destination support.** *(Doc-local rejection — MDX is React-family, not Astro-family; its destination handling lives in the React-family dispatch, outside framework-components scope.)* MDX (Markdown + JSX) appears in many Astro projects but is closer to React than to Astro — its destination handling lives in the React-family dispatch (`.mdx` falls through to `src/snippets/languages/tsx.ts` in `src/snippets/dispatch.ts`, served by the shared `src/snippets/_react.ts:buildReactImport` algorithm), not the framework-components scope. Astro's `ASTRO_SUPPORTED_EXTENSIONS` continues to list `.mdx` as a **source** (Astro's native `astro:content` collections API), which is unaffected by the React-family destination decision.
- **Fonts (`.woff`, `.woff2`, `.ttf`, `.eot`) as sources for framework SFCs.** *(Criterion D: Source-type-conditional / wrong shape — SFCs declare fonts via `@font-face` in `<style>`, not via a side-effect script import.)* SFCs declare fonts via `@font-face` inside their `<style>` block, not via side-effect `import './font.woff2';` in the script block. Wrong shape for this destination class. Fonts continue to work in JSX/TSX/MDX destinations via the existing `src/snippets/_react.ts:buildAssetImportStatement` side-effect group.
- **`.html` as a source for framework SFCs.** *(Fails Rejection Criterion B — bundler/framework-specific: Astro's `?raw` suffix import is bundler-specific.)* Vue / Svelte have no canonical use case for importing raw HTML. Skip across all three.
- **Exotic source extensions** (`.txt`, `.csv`, `.glsl` / `.frag` / `.vert` shaders, `.wasm`, `.proto`, `.graphql`). *(Fails Criterion 1: Frequency + Rejection Criterion B — bundler-specific plugin syntax: all are either too niche for the default picker or require bundler-specific plugin syntax.)* Revisit if user demand surfaces; otherwise out of scope.
- **Ember `.gjs` / `.gts` template-tag components** — *(Fails Criterion 1: Frequency.)* Modern Ember's Polaris format (RFC 0779) — single-file template + JS/TS via the `<template>` tag. Hits Standards-current (default in modern Ember docs, Glint typings, growing tool ecosystem), Framework-portable within Ember (same status `.vue` holds within Vue), and Modern best practice per the Ember core team. Fails the strong criterion — Ember sits at ~1–2% of frontend frameworks in 2026 (State of JS, npm trends), and growing-within-Ember doesn't help when the denominator is the whole ecosystem. The "first to support Polaris" play doesn't pay off because the audience overlap with this extension's user base is small in absolute terms, and Ember's own tooling story (Glint, embroider, official Ember VS Code extensions) already covers the import surface. Revisit triggers: a user issue requesting `.gjs` / `.gts` support, OR a measurable Ember resurgence in State of JS / npm trends, OR `create-ember-app` defaulting to Polaris.
- **Marko `.marko` single-file components** — *(Fails Criterion 1: Frequency + Rejection Criterion F: Picker bloat with low marginal value.)* Active framework (v6, eBay-built) with a unique single-file format. Real production use is concentrated at eBay + a handful of large e-commerce sites; broader audience is below 1% of frontend codebases. Marko developers typically already use the official Marko VS Code extension for imports, so the marginal user count for this extension's audience is near-zero. Skip; revisit only on direct user request.
- **Riot.js `.riot` single-file components** — *(Fails Criterion 1: Frequency.)* Maintained but quiet in 2026; audience is niche with no resurgence signal. Most users in this size class have migrated to Svelte / Vue. Skip.
- **Dedicated `script.vueImportStyle` setting** — *(Fails Rejection Criterion F: Picker bloat with low marginal value.)* Vue `<script setup lang="ts">` is TypeScript — the seven-entry TS picker covers Vue's import surface 1:1 with no semantic gap. A dedicated picker adds three-site sync overhead (`package.json` ↔ `_styles.ts` ↔ per-language `switch`) and a bloat-ceiling row for zero user benefit.
- **`.vue` ↔ `.svelte` cross-framework gating (Phase 2)** — *(Criterion 1: Frequency — mixed Vue+Svelte codebases are rare; the two frameworks are competitors, not complements.)* Interop path is `.js` (web components) or `.astro` (islands). The cross-framework story that ships is `.vue`/`.svelte` → `.astro` (Astro Islands) — that is where the real interop lives. Revisit if user demand surfaces.
- **Dedicated `script.svelteImportStyle` setting** — *(Fails Rejection Criterion F: Picker bloat with low marginal value.)* Svelte `<script lang="ts">` is TypeScript — the seven-entry TS picker covers Svelte's import surface 1:1 with no semantic gap. Same reasoning as the Vue equivalent.
- **`.vue` / `.svelte` destinations accepting `.astro` sources (Phase 3)** — *(Criterion 1: Frequency — `.astro` components are consumed exclusively by other `.astro` files; Vue/Svelte compilers can't process `.astro` syntax.)* Unlike the reverse direction (`.vue`/`.svelte` → `.astro` via Astro Islands, which IS in scope via `ASTRO_SUPPORTED_EXTENSIONS`), importing `.astro` into Vue/Svelte would produce broken code. Revisit only if an interop adapter surfaces.
- **Dedicated `script.astroImportStyle` setting** — *(Fails Rejection Criterion F: Picker bloat with low marginal value.)* Astro frontmatter is TypeScript — the seven-entry TS picker covers it 1:1 with no semantic gap. Same reasoning as Vue and Svelte equivalents.
