## 1. Context

The extension supports 12 destination languages (`.ts`, `.js`, `.jsx`, `.tsx`, `.mdx`, `.css`, `.scss`, `.html`, `.md`, `.vue`, `.svelte`, `.astro`). Two QA checklists already exist:

- `qa.new/checklists/general.md` — cross-destination shared behaviors (55 cases). Done.
- `qa.new/checklists/typescript.md` — `.ts`-specific behaviors (86 cases). Done by hand.

Eleven language-specific checklists remain. Writing them by hand risks **drift** — structural inconsistency, missed sections, wording divergence — which defeats the consistency goal. Hand-writing also produces no audit trail of how each checklist was derived, so maintenance over time becomes guesswork.

This spec defines a **spec-driven codegen pipeline** that treats checklist generation as a compilation problem. The hard analysis is done once and frozen; per-language generation becomes mechanical.

---

## 2. Mental model

```
source code  →  profile (IR)  →  checklist (output)
                     ↑
              human-reviewed, static
```

The IR is a static, hand-built, human-readable table — populated **once** by reading the actual extension source, then frozen. Every per-language generation reads from the same IR, so two runs cannot diverge. Consistency stops being aspirational and becomes structural.

Three properties this model gives us:

| Property | How it's enforced |
|----------|-------------------|
| **Consistency** | Single `RECIPE.md` + single `PROFILE.md` shared by all 12 destinations |
| **Determinism** | IR is frozen; no per-session re-analysis of source code |
| **Resumability** | Runbook state lives on disk as `[ ]`/`[x]` checkboxes |

## 3. Infrastructure layout

New subtree at `qa.new/_authoring/`, sibling to `checklists/` and `workspace/`. Underscore prefix follows the project's "internal/meta" convention (cf. `src/snippets/_styles.ts`, `_react.ts`, `_class-name.ts`).

```
qa.new/
├── checklists/                       (existing — human-facing QA artifacts)
│   ├── general.md
│   ├── typescript.md
│   └── ...                           (11 more, generated by this pipeline)
├── workspace/                        (existing — fixture trees)
│   ├── general/
│   ├── typescript/
│   └── ...                           (11 more, generated by this pipeline)
└── _authoring/                       (NEW — meta-docs, pipeline operational files)
    ├── README.md                     (what this subtree is, sync rules)
    ├── RECIPE.md                     (section recipe — codegen rule)
    ├── PROFILE.md                    (destination profile table — the IR)
    ├── LOOP-PROMPT.md                (reusable loop-prompt text)
    ├── runbook-{ext}-checklist.md    (Phase A runbook — committed alongside the checklist)
    ├── runbook-{ext}-workspace.md    (Phase B+C runbook — committed alongside the workspace + sync docs)
    ├── runbook-typescript-migration.md  (TS migration — single-session exception)
    └── parity-ts.md                  (disposable — exists only during TS migration)
```

| File | Lifecycle |
|------|-----------|
| `RECIPE.md` | Stable; rarely changes |
| `PROFILE.md` | Stable; one row added if the extension gains a new destination |
| `LOOP-PROMPT.md` | Stable; reused verbatim across all runbooks |
| `runbook-{ext}-checklist.md` | Committed alongside the checklist it produced (Phase A session) |
| `runbook-{ext}-workspace.md` | Committed alongside the workspace + sync-doc updates it produced (Phase B+C session) |
| `runbook-typescript-migration.md` | Committed alongside the regenerated TS checklist (single-session TS exception) |
| `parity-ts.md` | Disposable; lives only during the TS migration session |

## 4. The IR — `PROFILE.md`

One row per destination. Captures the four dimensions that actually vary across languages.

| Field | What it encodes | Example values |
|-------|-----------------|----------------|
| `gating` | Same-extension only, or cross-import? Which `*_SUPPORTED_EXTENSIONS` table applies? | `.js`: same-only • `.html`: cross via `HTML_SUPPORTED_EXTENSIONS` • `.vue`: cross via `VUE_SUPPORTED_EXTENSIONS` |
| `styles` | Single style table, source-type dispatch, or source-extension dispatch | `.js`: `JAVASCRIPT_IMPORT_OPTIONS` (7) • `.html`: dispatches on source type to 6 branches — 4 configurable tables (script/image/video/audio) + 2 fixed single-shape builders (stylesheet, text-track) • `.tsx`: TS table for `.ts`/`.tsx`, JS table for `.js`/`.jsx`, hardcoded fallthrough for non-script |
| `smartId` | Class detection? Angular PascalCase? | `.ts`: both • everything else: none |
| `pathQuirks` | Special path handling | `.scss`: `_partial` normalization + always preserve `.css` • `.html`/`.md`: always preserve full extension • everything else: respect `preserveScriptFileExtension` |

The table holds 12 rows (one per destination — `.tsx` and `.mdx` are separate rows even though `.mdx` is byte-identical to `.tsx`; see §10). Populated by reading the extension source code:

- `src/gating.ts` → `gating` field
- `src/snippets/variants.ts`, `src/snippets/dispatch.ts`, `src/snippets/_styles.ts` → `styles` field
- `src/snippets/languages/typescript.ts` (Angular legacy PascalCase: `LEGACY_ANGULAR_FILE_SUFFIXES`, `generateAngularLegacyImportName`), `src/snippets/_class-name.ts` (exported-class detection: `readExportedClassName` / `extractFirstExportedClassName`), `src/snippets/variants.ts` (only `.ts` case calls `readExportedClassName`) → `smartId` field
- `src/snippets/languages/scss.ts`, `src/snippets/languages/html.ts`, `src/snippets/languages/markdown.ts` → `pathQuirks` field

## 5. The codegen rule — `RECIPE.md`

Numbered section list. Each marked **required** or **conditional**, with conditions resolving against profile fields.

```
1.  Cross-import gating matrix              [required]
2.  Paste as Import — happy path            [required] — 1 case
3.  Insert Import from Selected File        [required] — 1 case
4.  All N styles                            [required] — N from profile.styles count
5.  Smart identifier behavior               [conditional: profile.smartId != none]
6.  Placement modes (Bottom / Top / Cursor) [required] — identical across languages
7.  Paste as Import (Pick Style)            [required]
8.  Set Default Import Style                [required]
9.  Drag-and-drop                           [required]
10. Edge cases                              [required]
11. Sign-off                                [required] — case-count summary
```

Plus per-quirk slots resolved from `profile.pathQuirks`:

- If `partial-filename-normalization` → add subsection under §4 demonstrating `_partial.scss` → `partial`
- If `always-preserve-css` → add §4 note that `.css` sources always include extension regardless of setting
- If `always-preserve-extension` → omit the `preserveScriptFileExtension` toggle tests entirely

**Fixture-content inlining rule.** For every fixture file the checklist references, the checklist must inline its expected content (in a fenced code block or inline assertion). This is what makes Phase B mechanical — without it, Phase B requires creative judgment to fill in fixture content, which defeats the per-language session split (§6). The existing `typescript.md` already follows this pattern (e.g., `destinations/with-require.ts` shows its `export const fs = require('fs');` content in the placement-test section); the rule just makes the convention explicit.

**Executable-instruction rule (no guessing).** Every actionable step must be runnable as-is in the Extension Development Host with zero inference. Each step names all three of:

1. **The exact fixture file** — a clickable workspace path (`typescript/src/foo.ts`), never "a TS file".
2. **The exact gesture** — a keybinding (`Cmd+Shift+A`, `Cmd+I`, `Alt+D`), a Command Palette entry (`Auto Import: Paste as Import (Pick Style)`), or a drag-source → drop-target pair.
3. **The exact expected result** — the literal inserted import string (`import { $1 } from './foo';`) or the verbatim toast (`Auto Import: Cannot import .js into .ts files.`).

Corollaries:

- A step gated on a setting names the exact setting label and value (`set Import Statement Placement to Top`).
- A step that mutates a destination file ends with the restore action (`Undo` / `Cmd+Z`) so the next step starts from a known state.
- A multi-step gesture spells out the order (copy source → open destination → press the paste key).

A table row pairing a source path with its verbatim expected output (as in the §1 gating matrix) is a valid executable form — the rule forbids *vagueness*, not tables. The anti-pattern is an abstract step like "copy a source file and paste it"; that is a defect, not a valid checklist item. The existing `typescript.md` is the reference shape.

Cross-import destinations (HTML, MD, CSS, SCSS, JSX, TSX, MDX, Vue, Svelte, Astro) also get an expanded §1 — instead of "everything except the destination extension is rejected" they enumerate accepted vs rejected sources from their `*_SUPPORTED_EXTENSIONS` table.

## 6. Per-language runbook

Each language has **two runbook files**, run in two separate sessions:

- `qa.new/_authoring/runbook-{ext}-checklist.md` — drives Phase A (checklist generation). Committed in its own session.
- `qa.new/_authoring/runbook-{ext}-workspace.md` — drives Phases B + C (workspace fixtures + sync-doc updates). Committed in a second session, after the checklist has landed.

Splitting this way gives Phase A — the only creatively-demanding phase — a dedicated agent context. Phases B and C are mechanical (file creation from explicit specs, template-fill into existing inventory tables) and bundle together cleanly. The TS migration is the one exception — see §7.

### Template A — `runbook-{ext}-checklist.md` (Phase A only)

```markdown
# Runbook — `.{ext}` checklist generation (Phase A)

> **CRITICAL — Two-tier checkbox rule.**
> The `[ ]` boxes in THIS file are for the agent to tick as it completes
> generation tasks. The `[ ]` boxes inside the generated
> `qa.new/checklists/{ext}.md` are for the HUMAN running QA in the
> Extension Development Host. **NEVER tick boxes in
> `qa.new/checklists/{ext}.md` during generation.**

## Phase A — Build checklist

- [ ] Read `qa.new/_authoring/PROFILE.md` row for `.{ext}`
- [ ] Read `qa.new/_authoring/RECIPE.md`
- [ ] Read source-of-truth files:
      - `src/snippets/languages/{ext-module}.ts` — per `dispatch.ts`:
        `.vue`/`.svelte`/`.astro` → `framework-component.ts`, `.mdx` → `tsx.ts`,
        all others → `{ext}.ts`
      - `src/snippets/_styles.ts`
      - `src/snippets/variants.ts` and `src/snippets/dispatch.ts`
      - `src/snippets/_class-name.ts`  (only smart-ID destinations: `.ts`)
      - `src/snippets/_react.ts`        (only React-family destinations: `.jsx` / `.tsx` / `.mdx`)
      - `src/gating.ts`
      - `src/constants/extensions.ts`
- [ ] Write `qa.new/checklists/{ext}.md` per recipe + profile,
      with expected fixture content inlined for every referenced path
- [ ] Self-verify: every recipe section the profile marks required is present
- [ ] Self-verify: no recipe section the profile excludes was emitted
- [ ] Self-verify: section 4 enumerates exactly N styles where N = profile.styles count
- [ ] Self-verify: every fixture path referenced has inline content described
- [ ] Self-verify: every actionable step is executable — names the exact fixture
      file, the exact gesture (keybinding / Command Palette entry / drag-drop),
      and the exact expected result; no step requires the tester to guess
```

### Template B — `runbook-{ext}-workspace.md` (Phases B + C)

```markdown
# Runbook — `.{ext}` workspace + propagation (Phases B + C)

> **CRITICAL — Two-tier checkbox rule.** Same as the checklist runbook.
> NEVER tick boxes in `qa.new/checklists/{ext}.md`.

> **Handshake prerequisite.** `qa.new/checklists/{ext}.md` MUST already exist
> on disk (committed by the prior checklist session). If it does not,
> stop and report — do not proceed.

## Phase B — Build workspace

- [ ] Verify `qa.new/checklists/{ext}.md` exists on disk
- [ ] Read it; extract every fixture path referenced and its inline content spec
- [ ] Create `qa.new/workspace/{ext}/` directory
- [ ] Create each fixture file with the exact content the checklist specifies
- [ ] Write `qa.new/workspace/{ext}/README.md` (file tree + fixture mapping)
- [ ] Write `qa.new/workspace/{ext}/CLAUDE.md` (edit rules)

## Phase C — Wire & propagate

- [ ] Update `qa.new/checklists/README.md` (inventory + case count)
- [ ] Update `qa.new/checklists/CLAUDE.md` (file table)
- [ ] Update `qa.new/README.md` (top-level mapping)
- [ ] Update `qa.new/CLAUDE.md` (top-level mapping)
- [ ] Update `qa.new/workspace/README.md` (languages table + counts)
- [ ] Validate: every path referenced in `{ext}.md` exists in `workspace/{ext}/`
- [ ] Validate: no orphan fixtures in `workspace/{ext}/`
      (or note as intentional in workspace README)
```

## 7. The TypeScript migration — validation fixture

> **TS migration is a single-session exception.** Unlike the 11 new-language migrations (which split into two sessions — checklist then workspace), TS migration runs in one session. The workspace already exists at `workspace/typescript/`, so Phase B is verification-only, not creation. The cognitive load is concentrated in Phase A.5 (parity gate), not in fixture work. Splitting TS would add ceremony without benefit. The runbook file is named `runbook-typescript-migration.md` to distinguish it from the two-file pattern used for new languages.

TS regeneration is the **stress test for the pipeline itself**. If RECIPE.md + PROFILE.md cannot reproduce the existing `typescript.md`, the infrastructure is wrong — discover that before generating any new language.

TS's runbook inserts two extra phases:

```markdown
## Phase 0 — Parity baseline (TS only)

- [ ] Extract test-case inventory from existing `qa.new/checklists/typescript.md`
- [ ] Save inventory to `qa.new/_authoring/parity-ts.md` as a flat list of cases

## Phase A.5 — Parity gate (TS only)

- [ ] Diff regenerated `typescript.NEW.md` against `parity-ts.md` inventory
      at test-case granularity
- [ ] List orphans (cases in old missing from new)
- [ ] For each orphan: patch PROFILE row or RECIPE entry, re-run Phase A
- [ ] Iterate until orphan list is empty OR all remaining deltas are
      documented as intentional improvements (reordering, consistency edits)
- [ ] Atomic swap: replace `typescript.md` with `typescript.NEW.md`
- [ ] Delete `parity-ts.md` (or copy contents into the commit body for audit)
```

**Phase B for TS is partially a no-op** — the workspace fixtures already exist. The Phase B tasks become "verify every path the regenerated checklist references exists; add fixtures only for any genuinely-new paths the regeneration introduced."

## 8. Loop prompt

Lives at `qa.new/_authoring/LOOP-PROMPT.md`. The user pastes this verbatim per session, substituting two placeholders: `{lang}` (e.g. `javascript`) and `{phase}` (one of `checklist`, `workspace`, or `migration`).

```
Read qa.new/_authoring/runbook-{lang}-{phase}.md.

Find the first task with `[ ]`. Execute it. Mark it `[x]` and save the runbook.
Repeat until no `[ ]` boxes remain.

Hard rule: NEVER tick `[ ]` boxes inside qa.new/checklists/{lang}.md.
Those belong to the human running EDH.

If a task fails or you need clarification, stop and report — do not skip.
```

Usage examples:

```
.js checklist session:    {lang} = javascript,  {phase} = checklist
.js workspace session:    {lang} = javascript,  {phase} = workspace
TS migration session:     {lang} = typescript,  {phase} = migration
```

Properties:

- **Idempotent.** Re-pasting after a partial run picks up at the first remaining `[ ]`.
- **Resumable across sessions.** Runbook state is on disk; conversation history is not required.
- **Two-axis substitution.** Only `{lang}` and `{phase}` change; everything else is verbatim.

## 9. Two-tier checkbox rule

The single most likely failure mode of this pipeline is **conflating the agent's task checkboxes with the human's QA checkboxes.** Get this wrong and the QA artifact ships with phantom "tested" marks.

| Tier | File | Audience | Lifecycle of `[ ]` |
|------|------|----------|--------------------|
| **Tier 1 — Procedural runbook** | `qa.new/_authoring/runbook-{ext}-{checklist,workspace,migration}.md` | Agent | `[ ]` → `[x]` as work completes |
| **Tier 2 — QA checklist** | `qa.new/checklists/{ext}.md` | Human in EDH | `[ ]` stays `[ ]` after generation; human ticks during manual QA |

**The runbook's header must restate this rule prominently.** Any future agent reading the runbook should encounter the rule before reaching the first `[ ]`.

## 10. Execution order

One commit per step. One session per step. Stop after any commit and the repo is in a working, consistent state.

```
1.   scaffold-authoring                     (empty _authoring/ + RECIPE + LOOP-PROMPT + PROFILE skeleton)
2.   populate-profile                       (PROFILE.md filled with all 12 rows)
3.   migrate-typescript                     (Phase 0 → A → A.5 parity → B verify → C; single session)
4a.  generate-javascript-checklist          (Phase A only)
4b.  generate-javascript-workspace          (Phases B + C)
5a.  generate-css-checklist
5b.  generate-css-workspace
6a.  generate-scss-checklist
6b.  generate-scss-workspace
7a.  generate-html-checklist
7b.  generate-html-workspace
8a.  generate-markdown-checklist
8b.  generate-markdown-workspace
9a.  generate-jsx-checklist
9b.  generate-jsx-workspace
10a. generate-tsx-checklist
10b. generate-tsx-workspace
11a. generate-mdx-checklist                 (PROFILE row identical to .tsx; generated independently)
11b. generate-mdx-workspace
12a. generate-vue-checklist
12b. generate-vue-workspace
13a. generate-svelte-checklist
13b. generate-svelte-workspace
14a. generate-astro-checklist
14b. generate-astro-workspace
```

Total: **25 sessions, 25 commits** (was 13 in the first draft, 23 before `.mdx` was split out).

### Why this order

| Step | Rationale |
|------|-----------|
| 1 → 2 | RECIPE is stable, PROFILE needs source-code analysis. Splitting lets RECIPE land as its own reviewable commit before the heavier IR work begins. |
| 3 (TS first) | TS is the most complex destination (smart-ID + Angular + 7 styles). If the pipeline can't reproduce `typescript.md`, RECIPE/PROFILE are wrong — discover that before generating 10 broken checklists. |
| 4 (.js) | Simplest comparison to TS — same gating model, fewer features. Validates that the smart-ID conditional in RECIPE correctly suppresses §5. |
| 5–6 (.css, .scss) | First stylesheet destinations — exercise `pathQuirks`. `.scss` stresses the rarest quirk (`_partial` normalization). |
| 7–8 (.html, .md) | Stress the source-type-dispatch style model. `.html` has 6 types; `.md` is the simpler 2-type cousin. |
| 9–11 (.jsx, .tsx, .mdx) | First cross-import script destinations; exercise the source-extension-dispatch style model. `.mdx` is byte-identical to `.tsx` (shared builder) but gets its own self-contained checklist — generated right after `.tsx`, independently from its own PROFILE row (no seed-from-sibling). |
| 12–14 (.vue, .svelte, .astro) | Framework components share the same `framework-component.ts` builder; same shape, three destinations. Doing them last lets the pipeline benefit from all prior stress tests. |

## 11. Per-session workflow

Each language requires **two sessions** in sequence: a checklist session (Phase A) followed by a workspace session (Phases B + C). The checklist session must commit before the workspace session begins — the workspace runbook's handshake task verifies the checklist exists on disk before doing anything else. The TS migration is the one exception: a single session that runs Phase 0 + A + A.5 + B (verify-only) + C in one go.

The per-session shape itself is identical (infrastructure and per-language alike):

```
┌─────────────────────────────────────────────────────────────────┐
│ Session N                                                       │
│                                                                 │
│  1. Enter plan mode                                             │
│  2. I read the inputs for this step (RECIPE / PROFILE / source) │
│  3. I propose a plan in the plan file                           │
│  4. You review and approve                                      │
│  5. Exit plan mode                                              │
│  6. For language sessions: I write the appropriate runbook      │
│     (runbook-{ext}-checklist.md OR runbook-{ext}-workspace.md)  │
│  7. For language sessions: You paste the LOOP-PROMPT             │
│  8. I tick through `[ ]` → `[x]` until none remain              │
│  9. You review deliverables                                     │
│ 10. ONE commit per session:                                     │
│       checklist session commits: runbook + checklists/{ext}.md  │
│       workspace session commits: runbook + workspace/{ext}/*    │
│                                  + updated sync docs            │
│ 11. Session ends                                                │
└─────────────────────────────────────────────────────────────────┘
```

This follows your `feedback_stepped_commits` rule at the session level: every step is plan-mode-gated and produces a single reviewable commit.

## 12. Guarantees the pipeline provides

| Guarantee | Mechanism |
|-----------|-----------|
| **Consistency across languages** | Static RECIPE + PROFILE — every language is rendered through the same templates over the same IR |
| **Determinism across sessions** | IR is frozen and human-reviewed; no per-session analysis re-derivation |
| **Resumability across sessions** | `[ ]` → `[x]` runbook state survives session death; loop picks up at first unchecked box |
| **Data preservation (TS migration)** | Parity gate refuses to ship until every test case in old `typescript.md` has a verified home in the regenerated file |
| **Audit trail** | Runbook files committed alongside their deliverables; `git log` shows exactly which procedure produced each checklist |
| **Sync safety** | Phase C is mandatory and validates `checklist ↔ workspace` 1:1, satisfying `qa.new/CLAUDE.md`'s propagation rule |
| **Agent isolation** | Each runbook phase is bounded to one cognitive mode (generation / fixture creation / wiring), preventing context-budget competition |
| **Executable QA artifact** | Every checklist step names file + gesture + expected result; the human tests by doing, never by guessing — enforced by §5's executable-instruction rule and the Phase A self-verify |

---

## 13. Failure modes the pipeline guards against

| Failure | Where it's caught |
|---------|-------------------|
| Agent ticks `[ ]` boxes inside `{ext}.md` (the human QA artifact) | Runbook header rule, explicitly stated at the top of every runbook |
| Workspace has fixture path the checklist doesn't reference, or vice versa | Phase C validation tasks |
| New style added to `_styles.ts` not reflected in checklists | Per-language Phase A rereads `_styles.ts`; section 4 count drift surfaces in self-verify step |
| RECIPE drift between languages | Single source of truth; structurally impossible |
| Context overload | Phase split keeps each invocation bounded |
| TS regression during migration | Parity gate blocks merge until orphan list is empty |
| Mid-session interruption | Loop prompt resumes at next `[ ]` |
| Profile drift across sessions | PROFILE is committed and read from disk every session |
| Two languages worked on in one session | Loop prompt is per-language; pasting it only drives one runbook |
| Skipping Phase C ("Wire & propagate") | Phase C tasks are part of the runbook; loop won't finish until they're `[x]` |
| Workspace session run before checklist session committed | `runbook-{ext}-workspace.md` Phase B first task verifies `qa.new/checklists/{ext}.md` exists on disk; halts with a clear error if not |
| Abstract / non-executable checklist step ("copy a source file and paste it") | Phase A self-verify enforces §5's executable-instruction rule — every step must name file + gesture + expected result |

## 14. Getting started

The very first action is **not** any language work — it's building the meta-infrastructure that everything else depends on.

**Session 1 — Infrastructure scaffold**

Single goal: lay down the empty `_authoring/` subtree and the stable artifacts. Nothing language-specific.

Deliverables (one commit):

```
qa.new/_authoring/
├── README.md            (what this subtree is, sync rules, how to use it)
├── RECIPE.md            (full section recipe — required/conditional rules)
├── PROFILE.md           (HEADER ONLY — table is empty; populated in Session 2)
└── LOOP-PROMPT.md       (reusable loop prompt text)
```

No `runbook-*.md` files. No language touched.

**Session 2 — Populate PROFILE.md**

Single goal: fill in all 12 rows by reading the actual extension source. One commit. End of Session 2, the IR is frozen and reviewable.

**Session 3 — TS migration**

Single goal: regenerate `typescript.md` through the pipeline + parity gate. After this, the infrastructure is proven.

**Sessions 4a–14b — Remaining 11 languages**

In the order listed in §10. **Each language takes two sessions**: a checklist session (Phase A) followed by a workspace session (Phases B + C). Twenty-two sessions total for the 11 languages, plus the three infrastructure sessions = **25 sessions, 25 commits** across the full migration.
